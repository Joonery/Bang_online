# BANG! 규칙 기반 봇 구현 설계 및 작업 계획

## 1. 목표와 설계 원칙

이 문서는 `BANG_RuleBased_Bot_Behavior_Spec_KO.md`를 현재 BANG! Online 코드에 적용하기 위한 구현 설계다. 핵심 목표는 다음과 같다.

- 게임 시작 전 로비에서 방장이 봇을 추가할 수 있다.
- 사람과 봇을 합친 참가자는 4~7명이며, 7명을 넘지 않는다.
- 봇은 사람 플레이어에게 공개되는 정보만 보고 같은 액션 검증 경로를 사용한다.
- 봇 전용 코드는 한 모듈에 집중하고, 엔진·서버·화면에는 필요한 연결 지점만 추가한다.
- 역할 목표, 생존, 사거리, 공개 장비, 손패 장수, 버린 카드 맨 위, 공개 로그를 함께 평가한다.
- 선택과 반응은 즉시 실행하지 않고 매번 임의의 사고 시간을 둔다.

## 2. 구조

### 2.1 `server/rule-based-bot.js`

봇 구현의 대부분을 이 파일에 둔다.

- `RuleBasedBangBot`: 한 봇의 기억, 역할 신뢰도, 카드 가치 계산, 대상 선택, 응답 선택을 담당한다.
- `BotBeliefModel`: 공개 로그를 증분 분석하여 각 플레이어의 무법자/보안관 편/배신자 가능성을 점수로 보관한다.
- `BotManager`: 여러 봇과 타이머를 관리한다. 상태 변경 때 행동 가능한 봇을 찾아 지연 후 정확히 한 액션을 실행한다.
- `BOT_NAMES`: 중복 없이 배정할 기본 이름 목록을 제공한다.

봇 클래스에는 `BangGame` 인스턴스를 전달하지 않는다. 대신 아래의 제한된 어댑터만 주입한다.

```text
BotGameApi
 ├─ getState(botId)       -> game.viewFor(botId)의 직렬화 가능한 공개 상태
 └─ perform(botId, action)-> 사람과 동일한 서버 액션 디스패처
```

따라서 봇은 다른 플레이어의 실제 역할이나 손패, 덱 순서에 접근할 참조 자체를 갖지 않는다.

### 2.2 게임 엔진의 최소 변경

- 플레이어 공개 모델에 `isBot` 표시를 추가한다.
- 공개 상태에 현재 관찰자에게 허용되는 `bangUsed`를 제공하여 불가능한 뱅 반복 시도를 막는다.
- 행동 로그에 공개 메타데이터를 선택적으로 기록한다. 공격자, 대상, 카드 종류 등 실제 테이블에서 모두가 본 정보만 담는다.
- 카드 사용 로그에 대상이 있으면 대상 이름도 표시한다.

로그 메타데이터는 숨은 역할이나 손패 내용을 포함하지 않는다. 봇의 역할 추론은 반드시 `view.log`에 들어온 이 공개 기록을 소비해서만 갱신한다.

### 2.3 서버의 최소 변경

- `POST /api/bot`을 추가한다. 로비에서 방장 토큰으로만 호출할 수 있다.
- 서버가 미사용 기본 이름을 무작위로 골라 봇 플레이어를 추가한다.
- 기존 액션 디스패처를 사람과 봇이 함께 사용한다.
- 상태가 바뀐 뒤 `BotManager.poke()`를 호출한다.
- 세션 종료·재시작 시 봇 타이머를 정리하거나 새 게임에 다시 연결한다.

봇은 SSE 연결이나 브라우저 토큰을 만들지 않는다. 다만 좌석에서는 항상 연결된 참가자로 보인다.

### 2.4 화면의 최소 변경

- 로비의 방장 액션에 `봇 추가` 버튼을 둔다.
- 총 참가자가 7명이면 버튼을 비활성화한다.
- 봇 좌석에 `BOT` 배지를 보여 사람 참가자와 구분한다.
- 추가 성공/실패는 기존 토스트와 실시간 상태 갱신을 사용한다.

## 3. 공개 정보 계약

봇이 판단에 사용할 수 있는 정보는 다음으로 제한한다.

- 자신의 역할, 캐릭터, 생명력, 손패 내용, 장비
- 공개된 보안관 역할과 죽은 플레이어의 공개 역할
- 다른 플레이어의 캐릭터, 생명력, 손패 장수, 공개 장비, 거리
- 버린 카드 더미 맨 위 카드와 현재 공개된 선택 카드
- 현재 턴/단계/응답자와 공개 로그
- 게임 종료 뒤 공개된 역할과 승리 진영

다른 생존자의 숨은 역할, 손패 내용, 덱 순서와 게임 객체 내부 배열은 봇 API에 노출하지 않는다.

## 4. 로그 기반 역할 추론

`BotBeliefModel`은 마지막으로 본 로그 ID 이후의 항목만 처리한다. 각 플레이어에 대해 다음과 같은 누적 점수를 관리한다.

- 보안관 직접 공격: 무법자 가능성을 크게 올린다.
- 보안관 공격자의 공격·장비 제거: 보안관 편 가능성을 올린다.
- 저체력 보안관을 향한 광역 공격: 무법자 가능성을 올린다.
- 공개된 사망 역할: 해당 플레이어의 추정을 확정한다.
- 시간이 지난 약한 단서는 감쇠하여 한 번의 행동으로 역할을 확정하지 않는다.

역할별 대상 선정은 이 신뢰도에 공개 위협도를 더한다. 공개 위협도는 생명력, 손패 장수, 공격 캐릭터, 무기·조준경·방어 장비, 사거리, 제거 가능성을 사용한다.

- 보안관: 자신을 공격한 사람과 높은 무법자 의심 대상을 우선하되, 보안관 편으로 추정되는 1 HP 대상은 마무리를 피한다.
- 부관: 보안관 공격자를 우선하고 보안관을 직접 공격하지 않는다.
- 무법자: 보안관을 핵심 목표로 삼되 초반에는 일부 확률로 자원을 보존한다.
- 배신자: 보안관을 최종 생존자로 남겨 두면서 현재 강한 진영을 약화한다. 보안관과 자신만 남으면 보안관을 공격한다.

## 5. 의사결정 순서

상태를 받을 때 봇은 다음 순서로 단 하나의 행동을 고른다.

1. 인물 선택: 역할·생존 성향에 맞춰 두 인물 중 하나를 고른다.
2. 필수 판정: 다이너마이트, 감옥, 술통/주르도네 카드 뒤집기 및 럭키 듀크 결과 선택.
3. 치명 대응: 빗나감!, 맥주, 결투/인디언 대응을 생명력과 보존 가치로 판단.
4. 특수 선택: 키트 칼슨, 제시 존스/페드로 라미레즈, 잡화점, 시드 케첨.
5. 자기 턴 카드 사용: 생존 카드와 장비, 드로우, 방해, 공격 순으로 후보를 점수화한다.
6. 턴 종료 및 초과 손패 버리기: 낮은 가치 카드를 먼저 버린다.

동점 후보에는 작은 무작위 가중치를 넣고, 명세의 자원 보존 원칙에 따라 사용 가능한 카드가 있어도 일정 상황에서는 턴을 끝낼 수 있다.

## 6. 주요 카드와 캐릭터 보정

- 1~2 HP에서는 맥주, 빗나감!, 술통, 야생마의 보존 가치를 높인다.
- 뱅은 사거리와 턴당 사용 제한을 확인하고, 윌리 더 키드/볼캐닉 예외를 반영한다.
- 결투·인디언은 보유 뱅 수와 현재 생명력에 따라 대응 또는 피해 수용을 고른다.
- 강탈·캣 벌로우는 위협적인 공개 장비를 손패보다 우선 대상으로 삼는다.
- 감옥은 보안관이 아닌 다음 차례의 위협 대상을 선호한다.
- 다이너마이트는 저체력 또는 유리한 상황에서는 설치 가치를 낮춘다.
- 키트 칼슨은 자신의 카드 가치뿐 아니라 다음 플레이어의 감옥·다이너마이트와 추정 진영을 고려해 남길 카드를 정한다.
- 럭키 듀크는 판정 목적에 맞는 성공 결과를 우선한다.
- 제시 존스는 손패가 많은 추정 적, 페드로 라미레즈는 가치 높은 공개 버린 카드를 선택한다.
- 시드 케첨은 저체력 또는 어차피 버릴 초과 카드가 있을 때 가치가 낮은 두 장을 회복으로 바꾼다.

## 7. 사람다운 지연과 동시성 안전

- 모든 봇 액션은 기본적으로 1.2~3.2초 사이의 독립적인 무작위 지연 뒤 실행한다.
- 인물/카드/대상/버릴 카드 선택과 판정 뒤집기에도 같은 원칙을 적용한다.
- 테스트에서는 환경 변수로 지연 범위를 수 밀리초로 축소할 수 있다.
- 한 봇에는 타이머 하나만 둔다. 실행 직전에 최신 공개 상태를 다시 읽어 이미 다른 응답으로 상황이 바뀌었는지 확인한다.
- 액션 성공 뒤에는 다음 상태 변경이 새 판단을 깨우며, 오류가 난 동일 상태에서는 짧은 실패 기록으로 반복 루프를 막는다.
- 세션 종료, 새 방 생성, 재시작 때 기존 타이머를 모두 해제한다.

## 8. 작업 계획

1. 공개 플레이어 모델과 공개 로그 메타데이터를 추가한다.
2. 공용 액션 디스패처를 분리하고 봇 전용 API 어댑터를 만든다.
3. `RuleBasedBangBot`, `BotBeliefModel`, `BotManager`를 구현한다.
4. 로비 봇 추가 API, 이름 중복 방지, 7인 제한, 세션 수명주기를 연결한다.
5. 로비 버튼과 봇 좌석 배지를 추가한다.
6. 단위 테스트로 정보 경계, 역할 추론, 필수 응답, 카드·대상 선택, 지연 실행을 검증한다.
7. 통합 테스트로 방장 권한, 최대 인원, 자동 인물 선택과 게임 진입을 검증한다.
8. 실제 브라우저에서 로비 추가와 게임 시작 흐름을 확인한다.

## 9. 완료 기준

- 방장은 로비에서 봇을 추가할 수 있고 7명에서 더 추가할 수 없다.
- 기본 이름은 일곱 후보 중 무작위이며 같은 방에서 중복되지 않는다.
- 봇이 인물 선택부터 모든 필수 응답, 턴 진행, 손패 정리를 멈춤 없이 수행한다.
- 봇 모듈은 `BangGame`이나 다른 플레이어 내부 객체를 직접 참조하지 않는다.
- 역할 판단은 공개 로그만 사용하며 비공개 역할·손패·덱을 보지 않는다.
- 각 행동에 실제 무작위 지연이 있고, 테스트에서만 짧게 조정할 수 있다.
- 기존 사람 플레이와 테스트가 회귀 없이 동작한다.

## 10. 구현 결과와 운영 설정

설계에 따라 다음 파일에 구현했다.

- `server/rule-based-bot.js`: 봇 이름, 로그 추론, 역할·카드·대상 평가, 필수 반응, 지연 스케줄러
- `server/server.js`: 봇 전용 공개 상태 어댑터, 공용 액션 디스패처 연결, 로비 API와 세션 수명주기
- `engine/game.js`: `isBot`, 공개 로그 메타데이터, 공개 뱅 사용 횟수
- `public/app.js`, `public/styles.css`: 방장용 봇 추가 버튼과 BOT 배지
- `tests/bot.test.js`, `tests/integration.test.js`: 판단·지연·장기 진행·로비 통합 검증

로비 API는 다음 요청을 받는다.

```http
POST /api/bot
Content-Type: application/json

{ "token": "방장 토큰" }
```

봇의 실제 사고 시간은 기본 1.2~3.2초다. 서버 테스트나 로컬 빠른 검증이 필요할 때만 다음 환경 변수로 바꿀 수 있다.

- `BOT_MIN_DELAY_MS`: 최소 행동 지연(기본 `1200`)
- `BOT_MAX_DELAY_MS`: 최대 행동 지연(기본 `3200`)

서버 어댑터는 `game.viewFor(botId)` 결과를 `structuredClone`한 뒤 봇에 전달한다. 이 복제 경계 덕분에 봇은 공개 상태 객체를 통해서만 게임을 관찰하며, 엔진 내부 플레이어·손패·덱 배열의 참조를 얻지 않는다.
